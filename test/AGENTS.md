# TICO Test Rules

## Scope

These rules apply to changes under `test/` in addition to the repository root
`AGENTS.md`.

## Test placement

Place a test in the narrowest directory that owns the behavior:

- Local implementation contract: `test/unit_test/<subsystem>/`
- PyTorch-to-Circle conversion and numerical parity: `test/modules/`
- Quantization workflow and integration: `test/quantization/`
- CLI `.pt2` conversion: `test/pt2_to_circle_test/`
- Performance behavior: `test/performance/`

Mirror the production subsystem and nearby naming conventions. Do not add an expensive
model test for behavior that can be proven with a small synthetic unit test.

## Test design

- Reproduce the requested behavior directly; avoid unrelated fixtures and model code.
- Use fixed random seeds and deterministic inputs.
- Use the smallest tensor shapes that preserve the relevant behavior.
- Assert output values and the structural property that the implementation promises.
- Add a negative or non-matching case for pattern-based transformations.
- Test relevant rank, shape, dtype, layout, constant, multi-user, and lifecycle edges.
- Use explicit `atol` and `rtol` values justified by the operation and dtype.
- Assert the expected exception type and message fragment for failure paths.
- Keep tests independent of execution order and global mutable state.
- Restore environment variables, registries, hooks, and module modes changed by a
  test.
- Use temporary directories for generated artifacts and allow the test framework to
  clean them up.

Do not test only that code executes without raising. A regression test should fail for
the original bug and identify the specific behavioral contract being protected.

## Environment constraints

Unit tests should run on CPU and without network access unless the behavior is
inherently backend-specific.

Do not require:

- remote checkpoints or datasets;
- Hugging Face authentication;
- user-specific files or absolute paths;
- a particular GPU or accelerator;
- a pre-existing output directory;
- files generated by another test;
- test execution in a particular order.

Mock external boundaries only when the real dependency is outside the unit under test.
Do not mock the behavior being validated.

## Numerical assertions

- Prefer exact equality for integer, shape, graph-structure, and metadata contracts.
- Use `allclose` only when floating-point behavior requires it.
- Choose tolerances from expected numerical error, not from the value required to make
  the test pass.
- Compare dequantized values as well as integer representations when qparams are part
  of the contract.
- For pass tests, compare outputs before and after the rewrite when computation
  changes.
- Avoid broad aggregate metrics when a direct tensor or graph assertion can localize
  failure more precisely.

## Skips and expected failures

- Add a skip only for a documented environment or feature constraint.
- Keep skip conditions narrow and include a reason.
- Do not use a skip or expected failure to hide a regression introduced by the same
  change.
- Remove obsolete skips when their condition is fixed.

## Validation order

1. Run the specific test or closest `-k` keyword.
2. Run the owning subsystem tests.
3. Run `./ccex test` for cross-cutting changes.
4. Run model tests only when model-family behavior changed or a small test cannot cover
   the contract.

Examples:

```bash
./ccex test -k <specific-test-or-keyword>
./ccex test
./ccex test -m <model-name-or-pattern>
```

A skipped, interrupted, or unexecuted test is not a passing test. Report the exact
commands and outcomes in the final response.
